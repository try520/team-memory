# 客户端项目规则：团队记忆（memory MCP）

> **放哪里**：Claude Code → 项目根 `CLAUDE.md`；Qwen Code → `QWEN.md`；Cursor → `.cursor/rules/memory.mdc`（alwaysApply）；其他支持 `AGENTS.md` 的客户端 → `AGENTS.md`。
> **为什么需要**：服务端的 `initialize.instructions` 不保证被客户端注入（实测 Qwen Code 会丢弃），模型也不会仅凭工具描述就主动读写。这份文件是客户端每次必注入的部分，用来把「开场读、结束写」变成硬流程。
> **边界**：这是提示词不是代码，无法 100% 强制；能强制的只有服务端的 428 门控（未读规则不能写）。要真强制，用客户端 Stop hook 调 `/healthz` 之外的自检接口。

## 极简版（只想要三行时用）

```md
## 团队记忆（memory MCP）
- 任务开始先调用 memory_get_rules，按索引「适用场景」选与本次业务最相关的主题 memory_read，覆盖本次要碰的代码和数据即停，不够再继续。
- 任务结束前必须执行「记忆强制检查」：命中任一条就 memory_write；无论是否命中都要写 journal（无事写「本次无需记录：原因」）。
- 最终回复的最后一行必须是「记忆：已更新 <文件>」或「记忆：本次无需记录。原因：<具体原因>」，缺这一行视为任务未完成。
```

## 完整版（推荐直接粘贴）

```md
## 团队记忆（memory MCP）— 必须遵守

本项目接入了团队记忆服务 `memory`（MCP，端点已绑定项目，工具不带 project 参数）。
它保存的是：结论、取舍、坑、代码位置、任务状态。代码和字段不在里面，按文档里的路径读仓库、按表名查库。

### 一、任务开始（每次任务的第一步，不得跳过）

1. **在读取仓库文件、调用任何其他工具之前，第一个工具调用必须是 `memory_get_rules`**，拿到 `session`、`user_name`/`user_name_source`、服务级规则、`RULE.md` 索引、`warnings`、`days_since_write`。
2. 用索引的「适用场景/举例」选出与本次业务最相关的主题 `memory_read`，覆盖本次要碰的代码和数据即停，不够再继续；不要一上来读整个 `topics/`。
3. 如果 `days_since_write >= 7` 或 `record_reminder` 非空：本次结束必须留下记录。
4. 写入必须带 `get_rules` 返回的 `session`；`RULE.md` 变了会返回 428，重新取规则，不要复用旧 session。

### 二、干活中

- 需要源码：按主题文档「代码位置」的路径直接读仓库，不要在本服务里找代码。
- 需要字段/索引：按文档写的表名直接查库，不要凭记忆。
- 改已有主题前先 `memory_read` 拿最新 `content` 与 `hash`；`replace` 必须带同一份 `expectedHash`，且 **content 必须是完整全文**，不得只提交一个片段。

### 三、任务结束强制检查（回复用户之前必须逐条核对）

逐条自问，**任一条为「是」就必须先完成对应写入，再回复用户**：

| # | 检查项 | 为「是」时写到哪里 |
|---|---|---|
| 1 | 是否定了方案或做了取舍（选了 A、否了 B、有原因）？ | 主题「结论」+「为什么」 |
| 2 | 是否踩了坑并解决（有现象、根因、规避办法）？ | 主题「坑」 |
| 3 | 接口/表结构/配置项/依赖版本是否变了（新旧值、影响范围）？ | 主题「结论」+「代码位置」 |
| 4 | 是否查到影响实现的关键结论（外部系统怪癖、限制、版本约束、责任人/入口）？ | 主题「结论」或「坑」 |
| 5 | 任务状态是否变化（开工/完成/阻塞/交接）？ | `TASKS.md`（开工先登记，完成后删行） |
| 6 | 是否有人纠正了记忆里的旧结论？ | 主题：新结论在前，旧结论标「（已废弃 YYYY-MM-DD，原因：…）」 |
| 7 | 是否有调试超过 30 分钟才定位的问题？ | 主题「坑」 |
| 8 | **无论如何**：本次会话是否已写 journal？ | `journal/YYYY-MM/<标题>.md`（≤300 字，标题写这次做了什么，服务端改名为 `<姓名>-<标题>-<hhmmss>.md`），无事写「本次无需记录：<具体原因>」 |

补充规则：

- **姓名不用你操心**：客户端配置里的 `X-Memory-User` 请求头会带上，服务端写进 TASKS「推进者」和 journal 文件名；只有临时想用别的名字时才在参数里传 `userName`（优先级：参数 > 请求头 > 会话标签）。
- **开工先占位**：只要本次要改 1 个及以上文件，先 `memory_write` 在 `TASKS.md` 登记一行六列——任务 / 状态 / 下一步 / 涉及文件 / 推进者（自报） / 更新时间，「涉及文件」写你要改的路径；纯问答、只读调研不必登记。判断占用不用另读文件：`memory_get_rules` 返回的 `tasks` 就是当前占用表（含 `files` 与 `owner`），要改的文件若出现在别人的行里，先说明并避开或沟通。写文件时若仍撞上，`warnings` 里会有 `TASK_CONFLICT`（提醒不是锁）；任务完成后立刻删掉自己那行。
- 新建主题必须同时给 `index.scene`（≤120 字，什么场景必须读）与 `index.examples`（2~3 个真实提问），否则返回 409；不要自己改 `RULE.md` 表格，交给服务端插入。
- 新建主题照五段写：`结论（现在就该这么做）` / `为什么` / `坑` / `代码位置` / `相关`，五段不得省略；「为什么」要写被否掉的方案。
- 只写结论：带具体值/表名/参数/路径；不写过程流水、不贴大段代码、不写密钥与客户真实数据；不确定的动机宁可不写，也不要编。
- `write` 返回的 `next` 是下一步提示，按它继续，不要写完就走。
- journal 文件名写这次做了什么（例如 `journal/YYYY-MM/修复登录超时.md`），服务端会改名为 `<姓名>-<标题>-<hhmmss>.md`；别用 `tmp`/`whatever` 这类占位名，服务端会退回正文首行当标题。**不要为取时间执行 shell 命令**（Windows 下 `date +%H%M` 不可用，实测会白掉一轮）。

### 四、固定收尾格式（硬性）

最终回复的最后一行必须是下面两种之一，缺这一行视为任务未完成：

```
记忆：已更新 topics/<主题>.md、journal/<年月>/<文件>.md
```

```
记忆：本次无需记录。原因：<具体到能复核，例如「只改了注释，无行为与接口变化」>
```

不允许写「记忆：无」「未记录」这类无法复核的表述；也不允许命中硬条件却写「无需记录」。

### 五、错误处理

| 返回 | 含义 | 动作 |
|---|---|---|
| `428 READ_RULES_FIRST` / `RULE_CHANGED` | 没读规则，或读完后 `RULE.md` 变了 | 重新 `memory_get_rules`，用新 `session` 重写 |
| `409 INDEX_ROW_REQUIRED` | 新建主题没给索引行 | 补 `index: {scene, examples:[…]}` 后重试 |
| `409 HASH_MISMATCH` / `EXPECTED_HASH_REQUIRED` | `replace` 的 hash 不对或缺失 | 重新 `memory_read`，合并后整篇 replace |
| `404 NOT_FOUND` | 路径不对 | 看返回的 `available` 列表，改用真实路径 |
```

### 六、首次接入已有项目：批量导入

当任务是把某个项目已有的规则/知识文档接入团队记忆时，不要一篇篇调 `memory_write`，用 `memory_import`：

1. **先摸清源**：用你自己的文件工具列出源文档、确认总量，不要一开始全读进上下文。
2. **先看索引**：源项目通常已有索引（如 `知识图谱.md` 的「文档 | 适用场景 | 举例」表）。这批人工写的场景/举例比自动生成的准，优先复用。
3. **分批读、分批导**：每批 5~10 篇或 ≤200KB；读一批调一次 `memory_import`，`files` 放原文，`path` 写 `topics/<文件名>.md`，`index` 带对应场景与举例。
4. **先预演**：第一批先 `dry_run: true`，看 `created` / `index_added` / `warnings` 是否符合预期，再正式跑。
5. **`rule_md`**：源索引本身就是 RULE.md 形态时，整理成 `## 文档索引` 三列表后整篇传入；merge 下只在索引为空时生效，重复导入不会覆盖。
6. **不要压缩原文**：导入保留原文，蒸馏留给后续按需做；更不要把上百篇塞进一次调用。
7. 导入后回一句汇总（导入 N 篇、索引 M 行、warnings 是否为空），再按服务级规则收尾写 journal。

`memory_import` 同样需要 `session`（先 `memory_get_rules`）；它可能改写 RULE.md 索引，若返回了新的 `session` 就用新的，否则沿用原值继续 `memory_write`。

## 验收方式（上线前自测）

在新会话里说一句**与记忆无关**的任务，例如「修一下 calc.go 的 Average 空切片问题」。合格标准：

1. 第一个工具调用是 `memory_get_rules`；
2. 任务完成后出现 `memory_write`（主题或 journal）；
3. 最终回复最后一行是「记忆：已更新 …」或「记忆：本次无需记录。原因：…」；
4. 新建主题带 `index.scene/examples`，五段齐全。

四条里缺任意一条，说明这份规则没有被客户端注入，或模型没有遵守——先查 `CLAUDE.md`/`AGENTS.md` 是否在项目根、是否被客户端读取。

## 实测（Qwen Code + glm-5.3-flash，同一任务）

| 配置 | 调 `get_rules` | 写主题 | 写 journal | 收尾「记忆：」行 |
|---|---|---|---|---|
| 不加客户端规则（5 轮：deepseek-flash / deepseek-pro / glm-flash / 手工注入 instructions ×2） | 0 | 0 | 0 | 无 |
| 本文件放进 `AGENTS.md` | 1 | 1 | 1 | 有：`记忆：已更新 topics/…、journal/…` |

代价：同一小任务从 4 轮 / 约 70 秒涨到 11 轮 / 约 198 秒，时间花在读规则、写主题、写 journal。
当轮观察到的两个偏差已回写进本文件：① 模型先读了 `calc.go` 再调 `get_rules`（已加硬顺序）；② 为取时间执行 `date +%H%M` 白掉一轮（已禁止）。
